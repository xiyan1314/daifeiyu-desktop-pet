# 错误留痕（追加型）

> **为什么有这个文件**：`_dev/VERIFY_DISCIPLINE.md` 第十三节采纳了审计员的建议——
> "同类错误第二次" 这条自检判据**在只有记忆时不可操作**（事后才成立、"同类"主观、也没法 grep）。
> 于是把每一次**已经发生过、且值得防第二次**的错误写成一条记录：谁、什么时候、什么形状、
> 怎么发现的、代价、防它的机制是什么。**只追加，不改历史**（唯一例外：**分类/计数写错时就地更正**，
> 并在文末「更正留痕」里留下原话与改动理由）。

**用法**：动手前 `grep` 关键字（例如"夹具"、"顺序污染"、"口径"）；
同一个家族第二次出现时，先问"上次那条防它的机制为什么没生效"。

> **⚠ 两个家族 + 计数口径（2026-10-16 · v2.10.0 发版轮 P2 · C-11 更正）**：本文件此前把下面
> **4 条记录**都写在"家族：夹具没有复原全局状态（运行顺序污染）"一个标题下、并写"**已发生 4 次**"——
> **两个家族被混在了一起，计数也跟着错**。正确口径：**3 起事故 / 4 条记录**
>（**假覆盖 2 起 / 2 条** · **运行顺序污染 1 起 / 2 条** = 加害方 #3 + 受害方 #4）。
> 改的是**分类与计数**；四条记录的**事实与代价一栏一字未改**（#2 的"位置"栏补了现树锚点，已注明）。
> 原话留痕见文末「更正留痕」。

## 家族一：假覆盖（断言永远不会红 / 从来没跑过）

**形状**：用例里的断言**结构上不可能失败**，或者**根本走不到** —— 那样跑出来的"绿"与"没写这条用例"
**在读结果时没有区别**。它比"没写"更坏：覆盖率、红绿、review 全部看起来正常。

**已发生 2 起事故 / 2 条记录**（本仓实测）：

| # | 时间 | 位置 | 怎么发现的 | 代价 |
|---|---|---|---|---|
| 1 | v2.9.0 第 7 轮 | `tests/test_io_v231.py::test_path_lock_merges_case_variants`：断言写在 Windows 走不到的分支里 | 变异第一遍 `NOT CAUGHT` | 一条断言在本机**从未执行过** |
| 2 | v2.10.0 第 8 轮 | `tests/test_dialogs_more_v24.py` 的 touched-flags 断言 `and`/`or` 优先级写错（原记录写"`:880`"；**该行号现在指向解释这段历史的注释**，断言本体已加强成 `assert dlg._touched_flags == {1}`，在 `:886`、用例 `test_role_edit_move_form_bounds_and_pending_follow`） | 人读出来 | 把 `_move_form` 的重映射删掉**照样绿** |

**已立的机制（这一族）**：恒真/弱断言守卫 `tests/test_assertion_strength_v2100.py`（扫 `tests/**`，
出现 恒真-T / 恒假-F / 死块-D 就红）＋ 它自己的"能真失败"证据（`M-C2100-R4-05` 把一句恒真断言原样塞回去、
守卫必须当场红）。
⚠ **但守卫只覆盖"结构上恒真"这一类**：#1 的"写在跑不到的分支里"与 #2 的"优先级写错"，**静态扫不出来**，
**只有变异能抓**（#1 就是变异抓出来的；#2 的加固有 `M-C2100-R4-04` 钉着：删掉那段重映射 →
`test_role_edit_move_form_bounds_and_pending_follow` 红）。逐条处置见 `_dev/README.md`
§零「恒真/弱断言 = 假覆盖」与「断言被平台条件藏起来」。

## 家族二：夹具没有复原全局状态（运行顺序污染）

**形状**：某个用例改了**模块级可变全局**（`pet_widgets.BUBBLE_STYLE` 这类就地 update 的 dict）
却不还原 → 后面的用例在"被污染的前提"上断言 → **单独跑绿、全量跑红**。
最坏的地方是它会**指向错误的方向**：红出来的那句断言看着像产品缺陷。

**已发生 1 起事故 / 2 条记录**（**#3 = 加害方 · #4 = 受害方，同一次事故**）：

| # | 时间 | 位置 | 怎么发现的 | 代价 |
|---|---|---|---|---|
| 3 | v2.11.0 第 9 轮 | `tests/test_feedback_host_v270.py` 把 `main.BUBBLE_STYLE` 改成 `#445566` 验成功路径、**不还原** | 全量 pytest 1 红、单跑绿 | 定版门红一次；误导方向指向产品代码 |
| 4 | v2.11.0 收尾 | 同 #3 的**受害方**：`test_motion_v2110.py::test_high_contrast_switch_applies_and_restores` 的"用户那份样式"前提被污染 | 同上 | 同上 |

**已立的机制**（本次）：`pet_widgets.BUBBLE_STYLE_CANON`（canon 的**独立副本**）
+ `test_motion_v2110.py` 的 `win` 夹具**建窗前 pinned 到 canon、建窗后逐项断言窗口真的拿着 canon 那一份、结束时复原进入时的全局值**。

**自查法（下次动手前）**：grep 你的用例里有没有对 `main.X` / 模块级 dict / 全局缓存的**写**；
有写就必须有还原（try/finally 或 fixture yield 之后），**并且**要在"污染源 + 受害用例"一起跑的形态下验证一次——
**只跑自己那个文件是测不出这类问题的**。

## 通用条目：**"单跑绿"不算过**

**规矩**：任何**修过夹具 / 改过全局状态 / 动过用例前提**的改动，验收读数必须是
**"污染源 + 受害用例一起跑"**的那个形态（理想是**全量**）。

- 只跑自己那个文件 → **污染源根本不在场** → 红被掩盖（或绿被伪造）；
- 反面同理：只跑受害用例 → 看不出"其实是我自己污染了别人"。

**教它的是「顺序污染」那一族**：上面 **#3 / #4（同一次事故）** 的第一次读数都是"单跑绿"，靠**全量跑**才发现。
（#1 / #2 属**假覆盖**族——它们的第一读数分别是**变异跑出 `NOT CAUGHT`** 与**人读出来**，**不是单跑绿**；
防它们的机制是变异 + 恒真/弱断言守卫，见家族一。）
⚠ 本条此前写"本仓已付出**四次**代价"、"四次里有**三次**的第一次读数是单跑绿"——那是**家族分类混了的连带错**，
随 C-11 一并更正；**留痕里的实际实例就是 #3/#4 这一起**。

**操作口径**：报告里写"已修/已过"时，**必须同时写清是在哪种形态下过的**
（单文件 / 相关文件组 / 全量）。**只写"passed"不写形态 = 无法复核。**

## 通用条目：**"grep 不到 ≠ 没覆盖"**

**来历（这条是被实测反例教出来的，不是推出来的）**：质量审 §1c 第 1 条 ①
（`_r3_quality_critic/review_v2110_quality.md`）用"`tests/test_config_robustness.py` grep `reduce_motion` /
`high_contrast` = **0 命中**"推出"**修了没钉子**"。**实测反例**（v1 交接 §9.2 抽检 1）：删掉 `pet_config.py`
里那两键的归一化 → `tests/test_config_robustness.py` **FAILED 并点名 10 条**（两键 × 5 个坏值）。

**为什么 grep 不到**：那条用例**不写字面键名**——它遍历 `main.DEFAULT_CONFIG.items()`
（`tests/test_config_robustness.py:70`），对 str 默认值灌 `POISON_STR`（`:16` = `[None, [], {}, 123, True]`，5 个），
再用 `_type_ok`（`:51-64`，`isinstance(default, str)` 那一支）要求归一化后仍是 str；
而 `reduce_motion` / `high_contrast` **就在 `DEFAULT_CONFIG` 里、默认值就是 str**（`桌宠.py:247` / `:250`）。

**我独立复核（2026-10-16，只读、未删任何代码）**：`grep "reduce_motion|high_contrast" tests/test_config_robustness.py`
→ **0 命中**；`:70` / `:16` / `:58-59` 与 `桌宠.py:247` / `:250` 的原文**逐条对上** → **2 键 × 5 坏值 = 10 条**，
与"点名 10 条"**数目相符**。（"删掉 → FAILED 点名 10 条"那句本身**是代理自述、我未复核**——复核它要改
`pet_config.py`，不在本轮许可内。）

**规矩**：**"某关键字 grep 不到"只说明"这个写法不存在"，不说明"这条路径没被覆盖"。**
判"有没有钉子"要么**跑一次还原**（删掉实现 → 看它红不红），要么**走 AST / 数据驱动**看用例到底覆盖了哪些键
（遍历 `DEFAULT_CONFIG` 的用例对**每一个 str 键**都成立，与键名有没有被写出来无关）。

**出处**：`_dev/REMAINING.md` C-16 与 §9.6（质量审同条的 ① 已被推翻；② "语义窄化"**仍成立** → C-16）。

### R-04（本轮 P9 · F1 的 `ActionPanel`）**新 UI 面要不要进"设计尺寸清单"** —— 本轮裁决：**不进**

**事由**：v2.10.0 发版轮的 F1 给「资源管理」加了第 4 页签「动作」（`pet_dialogs.py:5170`
`class ActionPanel(QWidget)`，`:5391` `self._tabs.addTab(self._action_panel, "动作")`）。
`tests/test_dialog_fit_v250.py` 那份"窗口清单"里**没有它**，于是要问一句：
**新加的 UI 面要不要进这张清单？**

**实测（2026-10-16 · 本轮，只读）**：

| 量 | 读数 | 命令 / 锚点 |
|---|---|---|
| 清单现在有几条 | **20 条** | AST 数 `_factories()` 返回的元组（文件里的注释仍写「19 个窗口」——那是 `PluginManagerDialog` 登记之前的旧数，**不比注释**） |
| `ActionPanel` 在**尺寸面**（`tests/test_dialog_fit_v250.py`）里的命中 | **0** | `grep "ActionPanel" tests/test_dialog_fit_v250.py` |
| `ActionPanel` 在**功能面**的覆盖 | **有：6 处引用 `dlg._action_panel`**（`tests/test_dialogs_v2100_round.py:526/543/571/602/626/672`） | F1 自己的用例：页签接线（:521）/ 只读清单（:537）/ 删除落盘（:565）/ 状态行交代（:597）/ 定位到所属角色（:620）/ 库不可用不崩（:667）。**别把下面那句读成「F1 没覆盖」——缺席的只有尺寸这一条线** |
| ResourceManagerDialog 的设计尺寸 | `(700, 560)` | 源码 `pet_dialogs.py:5381` `clamp_dialog(self, 700, 560)` ↔ 用例表 `tests/test_dialog_fit_v250.py:324` `"ResourceManagerDialog": (700, 560)`，两边仍然一致 |

**裁决：不进。** 三条理由（口径，不是个例豁免）：

1. **这张清单的判据对象是"自带设计尺寸的顶层窗口"** —— 它的四条判据（不超屏 / 内容滚得到底 /
   底排按钮行可见 / 实际尺寸**恰好**等于设计尺寸）都建立在"这个类自己那次 `clamp_dialog(W, H)`"
   上。`ActionPanel` 是**嵌在页签里的 QWidget 面板**（`tests/test_dialog_fit_v250.py:155-157` 的口径原文：
   面板不是顶层窗口、"没有底排按钮行这回事、尺寸由容器钳制"），它没有自己的 `clamp_dialog`、
   也没有 `_btn_row`——把它塞进"设计尺寸"表只会得到一条**测不到东西**的条目。
2. **它的尺寸契约由容器承担，而容器已经在清单里**：`ActionPanel` 拿的是
   `ResourceManagerDialog` 的 `clamp_dialog(700, 560)` + 页签布局算出来的尺寸，
   `ResourceManagerDialog` 那一条设计尺寸（`:324` 的 `(700, 560)`）与源码 `:5381` 今天仍然逐字一致，判据照旧守着。
3. **F1 没有新增顶层窗口** —— 它新增的是页签内容。清单的登记门槛是"新增了一个有自己设计尺寸的顶层窗口"；
   按这条门槛，本轮**没有**新面要登记。

**⚠ 同时如实登记这处空缺（不读成"已覆盖"）**：清单里那三个老面板（`RolePanel` / `SoundPanel` /
`VoiceAssetPanel`，`tests/test_dialog_fit_v250.py:133-135`）是**在**清单里的，靠 `NO_BUTTON_ROW`（`:157`）
跳过"按钮行"那一段 —— 面板级的"不超屏 / 滚得到底"对它们是成立的。`ActionPanel` **连这一段也没有**：
它只在 `ResourceManagerDialog` 被构造时**顺带**建出来（`:5390`），
**尺寸判据这条线上没有任何一条断言看着它**（功能面的 6 处见上表）。所以：

- 谁要声称"F1 的新页面尺寸也验过了"，**先看这段**——本轮**没有**这条证据；
- 下一次动 `ActionPanel` 的布局（加列 / 加按钮 / 改滚动结构）时，正确做法是**把它加进
  `_factories()` 与 `NO_BUTTON_ROW`**（面板级的两条判据即可），而不是往 `_DESIGN_SIZES` 里加一条假的设计尺寸。

**这条是口径不是豁免**：它只解释"为什么本轮清单不扩"，**不改**任何判据的形状，也不放宽任何比例
（`DIALOG_MAX_RATIO == 0.85` 与 `HARD_MAX_SMALL = (870, 510)` 原样，由 `test_上限就是85百分比而不是写死像素` 钉着）。
